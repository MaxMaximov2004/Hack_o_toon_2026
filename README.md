# Экосистема коммерческого блока — Радар присутствия

Хакатон осень 2026, кейс Ростелекома. **Сначала делаем продукт 1 — «Радар присутствия»** (карта
«как выбор ПВЗ» с нашими и не нашими клиентами двумя цветами, фильтры, белые пятна, экспорт, вход с 2FA). Продукт 2 («Инвестиционный навигатор»)
начинаем только после того, как продукт 1 собирается одной командой и проходит смоук.

## Запуск — одна команда

```bash
docker compose up -d --build
```

Открыть http://localhost, войти `demo@rt.ru` / `Demo2026!`, код — из аутентификатора с секретом
`JBSWY3DPEHPK3PXP`. Старый синтаксис `docker-compose up -d --build` тоже работает.

| Нужно | Команда |
| --- | --- |
| Пересоздать БД с нуля (после правки таблиц или сида) | `docker compose down -v && docker compose up -d --build` |
| Поднять только БД для локальной разработки | `docker compose up -d postgres` |
| Поднять БД + свой сервис | `docker compose up -d --build postgres core-api` |
| Логи сервиса | `docker compose logs -f core-api` |
| Зайти в БД | `docker compose exec postgres psql -U postgres -d radar` |
| Продукт 2 (добавляет notifier) | `docker compose --profile product2 up -d --build` |
| Смоук-проверка сборки | `bash infra/smoke.sh` |

## База данных

Всё создаётся контейнером `postgres` при первом старте из `infra/db/init/` (по алфавиту):

| Файл | Что делает |
| --- | --- |
| `01_roles_and_schemas.sh` | 5 пользователей БД и 5 схем, у каждой роли комментарий — чей это сервис и на каком языке |
| `02_tables.sql` | первая миграция: все таблицы всех сервисов (каждый блок — от имени роли-владельца) и функция `core.refresh_municipality_stats()` — единая формула потенциала и белых пятен |
| `03_seed.sql` | сид: клиенты РТ из таблицы кейса (`etl.raw_clients` — 759), инвестпроекты (`etl.raw_invest` — 63), справочники калькулятора (`calc.*`) |

`03_seed.sql` генерируется: `python3 infra/db/tools/gen_seed.py infra/db/tools/case.xlsx infra/db/init/03_seed.sql`.

**Правила:**

1. Один сервис — одна схема — один пользователь БД. Чужая схема отвечает `permission denied` — это так задумано.
2. Чужие данные — только по HTTP (`/api/*` или `/internal/*` с `X-Internal-Token`). Никаких кросс-схемных запросов.
3. Исключение одно: ETL (`etl_loader`) пишет данные в `core`, но не может менять её структуру.
4. **Сервисы не создают и не меняют таблицы из кода.** Никакого Flyway, `ddl-auto=update`, EF `Migrate()`,
   auto-migrate. Структура — только в `infra/db/init`. Нужна колонка → PR техлиду с новым файлом
   `04_<что>.sql` (или правкой `02_tables.sql` до первой общей сборки) → все делают `down -v && up -d`.

## Требования к каждому сервису — без этого PR не принимается

1. **`Dockerfile` в корне своей папки.** Multi-stage, финальный образ — только рантайм. Сборка не ходит в сеть к нашим сервисам.
2. **Фиксированный порт** из таблицы выше. Внутри docker-сети соседей зовём по имени: `http://core-api:8080`, `postgres:5432`. Никакого `localhost` в коде.
3. **Конфиг только из переменных окружения**, имена — ровно как в `docker-compose.yml`. Секретов в коде нет.
4. **`GET /health`** без авторизации → `200 {"status":"ok"}`. Проверяется через nginx: `/healthz/<сервис>`.
5. **Старт без соседей.** Если БД или сосед ещё не поднялся — повторять попытки (каждые 2 с, до 60 с), а не падать. JWKS у auth-service запрашивать лениво и кэшировать.
6. **Логи — в stdout**, по строке на событие.
7. **Перед PR проверено у себя:** `docker compose up -d --build postgres <свой-сервис>` поднимается с нуля, `/health` отвечает, эндпоинты отвечают по контракту.

## Как собираем: участник пушит → техлид поднимает одной командой

**Участник**, когда его часть готова (или раз в 2–3 часа, если готова частично):

1. Ветка `feat/<сервис>-<что>`, в PR — только своя папка. Изменения в `docker-compose.yml`, `infra/` или контракте — отдельно, через техлида.
2. В описании PR: что готово, что заглушено, как проверить (2–3 `curl`).
3. Squash-merge в `main` после ревью техлида.

**Техлид** после каждого слияния (и обязательно в «точки сборки» — раз в 3–4 часа и за 3 часа до сдачи):

```bash
git pull
docker compose down -v               # чистая БД, как на чужой машине
docker compose up -d --build         # ОДНА команда, без ручных шагов
docker compose ps                    # все running (etl — тоже: это сервис, грузит данные при старте)
bash infra/smoke.sh                  # контейнеры, загрузка ETL, /healthz, данные, изоляция схем, демо-сценарий
```

Затем вручную проходится демо-сценарий в браузере на телефоне. Если что-то красное — `docker compose logs <сервис>`,
владельцу пишется в чат, `main` не трогаем до починки. Зелёная сборка помечается тегом `p1-build-N` —
на защите показываем последний зелёный тег.

Если чьей-то папки ещё нет в `main`, промежуточную сборку поднимаем, перечислив готовые сервисы:
`docker compose up -d --build postgres etl auth-service core-api nginx`. nginx стартует без
отсутствующих соседей (адреса резолвятся в момент запроса), их маршруты отдают 502. Зелёный смоук
и тег — только когда поднимается всё одной командой `docker compose up -d --build`.
