**Владелец:** Python-разработчик. **Папка:** `etl/` (+ инструмент `tools/rmsp/prepare_rmsp.py` уже готов).
**Запуск:** контейнер `etl` в compose — разовый, стартует после БД, заливает данные и завершается с кодом 0.
**БД:** пользователь `etl_loader`. Своя схема `etl` (сырьё), в `core` — только данные (INSERT/UPDATE/DELETE/TRUNCATE).
Создавать и менять таблицы нельзя — структура в `infra/db/init/02_tables.sql`, нужна колонка → PR техлиду.
**Стек:** Python 3.12, psycopg 3 (`COPY`), стандартная библиотека. pandas — по желанию.

## Команда `python -m etl load` — по шагам

### 1. Загрузить сырьё

- `etl/data/rmsp_61.csv.gz` → `COPY etl.raw_rmsp (…24 колонки…) FROM STDIN WITH (FORMAT csv, HEADER true)` — через
  `cursor.copy()` в psycopg 3, построчно из `gzip.open`. Формат файла задаёт `prepare_rmsp.py`. Проверено на тестовой выгрузке.
- Если есть `data/revenue_fns.csv.gz` — так же в `etl.raw_revenue`.
- Файла реестра нет → ETL всё равно отрабатывает только на клиентах (759) и пишет `WARN` — чтобы сборка не падала до выгрузки.

### 2. Нормализация муниципалитета (для обоих источников)

В сырье десятки вариантов одного места: `АКСАЙСКИЙ РАЙОН`, `Аксайский Район`, `Аксайский р-н`, `ГОРОД РОСТОВ-НА-ДОНУ`, `г. Ростов-на-Дону`.

1. Источник: `district`, если не пустой, иначе `city`.
2. Нижний регистр, схлопнуть пробелы. `^(город|г\.)\s*(.+)$` → `г. ` + название; `^(.+?)\s*(район|р-н)$` → название + ` р-н`.
3. Заглавная буква в каждой части через дефис, кроме `на`, `в`: `Ростов-на-Дону`, `Матвеево-Курганский`, `Каменск-Шахтинский`.
4. `kind` = `city` для `г. …`, иначе `district`.

В Ростовской области 43 района и 12 городских округов — после нормализации должно получиться не больше ~55 значений.
Больше → в данных осталось разное написание, смотреть глазами.

### 5. Координаты и выручка

Все «случайности» — от хэша ИНН: `u(inn, salt) = int(sha256(inn + salt)[:8], 16) / 0xFFFFFFFF` → 0..1.
Стабильно между запусками и не зависит от порядка строк.

**Координаты** — точка рядом с центром населённого пункта (если есть в `settlements.json`) или муниципалитета:

```
R = 0.01° для населённого пункта, 0.03° для города, 0.08° для района
r = R * sqrt(u(inn, "r")),  φ = 2π * u(inn, "phi")
lat = lat0 + r * cos(φ)
lon = lon0 + r * sin(φ) / cos(lat0 в радианах)
```

**Выручка из ФНС** (если скачали `revenue_fns.csv.gz` — открытые данные ФНС «Сведения о суммах доходов и расходов» по
бухотчётности, только юрлица): `revenue_est` = доход за последний год, `revenue_growth_est` = рост к предыдущему году, если
есть оба года; `revenue_source = 'fns'`, `is_estimated = false`. Формат набора проверить при скачивании.

**Модельная выручка** для остальных (`revenue_source = 'model'`, `is_estimated = true`):

```
медиана: micro — ИП 4 млн, ЮЛ 15 млн; small — 250 млн; medium — 1,2 млрд
k_отрасли: trade 1.3, energy 1.4, manufacturing 1.2, logistics 1.1, construction 1.1, agro 1.0,
           it 0.9, realestate 0.8, other 0.8, services 0.7, hospitality 0.6
если известна численность: медиана = employees × 3 млн
revenue = медиана × k_отрасли × exp(0.6 × (u(inn, "rev") − 0.5) × 2)
обрезать по границам категории: micro ≤ 120 млн, small 120–800 млн, medium 800 млн – 2 млрд

возраст = 2026 − год(registered_at); база роста: < 2 лет → 25 %, 2–5 → 12 %, > 5 → 5 %
growth = база + 16 × (u(inn, "g") − 0.5)          # ±8 п. п., округлить до 0,1
```

### 6. Статистика районов — одна функция в БД

```sql
SELECT core.refresh_municipality_stats();   -- возвращает число белых пятен (industry = 'all')
```

Формула — в `infra/db/init/02_tables.sql`, общая для ETL и core-api (core-api вызывает её после импорта клиентов):

```
base_score  = 100 × (0.5·pr(компаний) + 0.3·pr(доли новых) + 0.2·pr(выручки))     pr — процентиль среди районов, по отрасли
gap         = 1 − охват_района / охват_по_области           (охват = клиентов / действующих компаний; не меньше 0)
potential   = base_score × gap
белое пятно = gap ≥ 0.5  И  base_score ≥ 65  И  компаний ≥ 30
```

Почему относительный охват, а не «ноль клиентов»: районы в кейсе взяты из адресов самих клиентов, поэтому почти в каждом
районе есть хотя бы один клиент — правило «0 клиентов» на всей области ничего не найдёт. Проверено на 200 000 синтетических
компаний: функция считается ~170 мс, `reason` выглядит как
`"3772 компаний, охват РТ 0.21% при среднем по области 2.02%"`.

**Калибровка на реальных данных — твоя задача:** `SELECT core.refresh_municipality_stats(60, 20)` и т. п., пока белых пятен
для `industry = 'all'` не станет 3–8 и они не будут выглядеть осмысленно. Выбранные числа — PR техлиду: он меняет значения
по умолчанию в функции, чтобы ETL и core-api считали одинаково.
