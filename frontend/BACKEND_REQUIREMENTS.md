# Требования к бэкенду для расширения поиска

## Текущее состояние (реализовано в core-api)

Параметр `q` в `/api/companies` ищет по следующим полям:

```sql
(c.name ILIKE '%' || :q || '%' ESCAPE '\' OR c.inn LIKE :q || '%' ESCAPE '\')
```

**Что работает:**
- Поиск по части названия компании (без учёта регистра)
- Поиск по началу ИНН

**Файл:** `core-api/src/main/java/ru/rt/radar/radar/filter/CompanyFilterSql.java:76-77`

## Предложения по улучшению (опционально)

Следующие улучшения могут сделать поиск более удобным, но НЕ требуют создания новых эндпоинтов — только расширение существующей логики параметра `q`:

### 1. Поиск по ОКВЭД (коду и названию)

**Зачем:** Пользователи часто знают код вида деятельности (например, «62.01» или «Разработка программного обеспечения»).

**Как реализовать:**
```sql
(c.name ILIKE '%' || :q || '%' ESCAPE '\'
 OR c.inn LIKE :q || '%' ESCAPE '\'
 OR c.okved_code LIKE :q || '%' ESCAPE '\'
 OR c.okved_name ILIKE '%' || :q || '%' ESCAPE '\')
```

**Влияние на производительность:** Минимальное, т.к. поиск уже использует ILIKE. Индекс на `okved_code` может ускорить точные совпадения.

### 2. Поиск по населённому пункту (settlement)

**Зачем:** Пользователи могут искать «Батайск» или «Новочеркасск», не выбирая район из фильтра.

**Как реализовать:**
```sql
(c.name ILIKE '%' || :q || '%' ESCAPE '\'
 OR c.inn LIKE :q || '%' ESCAPE '\'
 OR c.settlement ILIKE '%' || :q || '%' ESCAPE '\')
```

**Примечание:** `settlement` может быть NULL, но PostgreSQL корректно обработает это в условии OR.

### 3. Поиск по контактам (телефон, email, website)

**Зачем:** Поиск компании по известному телефону или домену сайта.

**Как реализовать:**
```sql
(c.name ILIKE '%' || :q || '%' ESCAPE '\'
 OR c.inn LIKE :q || '%' ESCAPE '\'
 OR c.phone ILIKE '%' || :q || '%' ESCAPE '\'
 OR c.email ILIKE '%' || :q || '%' ESCAPE '\'
 OR c.website ILIKE '%' || :q || '%' ESCAPE '\')
```

**Влияние на производительность:**
- Эти поля возвращаются только в полной карточке `Company`, не в `CompanyShort`
- Поиск по ним может быть медленным без индексов
- Рекомендуется добавлять индексы: `CREATE INDEX idx_company_phone ON company(phone) WHERE phone IS NOT NULL;`

### 4. Полнотекстовый поиск (опционально, продвинутый вариант)

**Зачем:** Быстрый поиск по нескольким полям с учётом морфологии русского языка.

**Как реализовать:**
```sql
-- Добавить колонку
ALTER TABLE company ADD COLUMN search_vector tsvector;

-- Создать индекс
CREATE INDEX idx_company_search ON company USING GIN(search_vector);

-- Триггер для автоматического обновления
CREATE TRIGGER company_search_vector_update
BEFORE INSERT OR UPDATE ON company
FOR EACH ROW EXECUTE FUNCTION
tsvector_update_trigger(search_vector, 'pg_catalog.russian',
  name, okved_name, settlement);

-- Использование в SQL
WHERE search_vector @@ plainto_tsquery('russian', :q)
```

**Плюсы:**
- Быстрый поиск по большим объёмам данных
- Учёт словоформ («логистика» найдёт «логистический»)
- Ранжирование результатов по релевантности

**Минусы:**
- Требует миграции БД и перестроения индекса
- Сложнее в поддержке

## Что НЕ нужно от бэкенда

1. **Новый эндпоинт для поиска** — существующий `/api/companies?q=...` достаточен
2. **Автодополнение на бэкенде** — фронтенд использует справочники из `/api/dictionaries` и топ-5 из `/api/companies`
3. **Хранение истории поиска** — не требуется по ТЗ

## Приоритизация

**Высокий приоритет (если есть время):**
- Поиск по ОКВЭД (код и название) — часто используется бизнесом

**Средний приоритет:**
- Поиск по населённому пункту — удобно, но можно использовать фильтр по району

**Низкий приоритет:**
- Поиск по контактам — редкий сценарий
- Полнотекстовый поиск — оптимизация для большой нагрузки, сейчас не критично

## Тестирование

После расширения `q` проверить:
1. Поиск по существующим полям (название, ИНН) не сломался
2. Новые поля корректно находятся
3. Спецсимволы экранируются (`escapeLike` работает)
4. Производительность на ~200 000 записей остаётся приемлемой (< 100 мс)
